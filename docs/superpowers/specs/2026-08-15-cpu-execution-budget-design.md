# Unified CPU Execution Budget Design

**Date:** 2026-08-15

**Status:** Architecture A approved by the operator; end-to-end f64 feature correction pending independent re-review

**Scope:** NeoEthos build parallelism and aggregate CPU-bound execution limits across the root, `mcp`, and `mesh` Cargo workspaces and the process trees NeoEthos manages

## Objective

NeoEthos must use the machine it is actually allowed to use, while leaving capacity equivalent to one SMT core free for operating-system stability. This is an aggregate ceiling for CPU-bound NeoEthos work in one managed process tree, not a separate allowance that every pool and child may consume again. In portable terms, the default CPU-work ceiling is:

```text
effective_available_logical_threads = std::thread::available_parallelism()
reserved_logical_threads            = min(2, effective_available_logical_threads - 1)
automatic_worker_limit              = max(1, effective_available_logical_threads - 2)
effective_worker_limit              = min(
                                        automatic_worker_limit,
                                        persistent_requested_limit if present,
                                        legacy_persistent_limit if present,
                                        parent_assigned_limit if present
                                      )
```

Every requested limit is optional and must be positive. Each one may narrow the automatic ceiling, but none may restore the two reserved logical threads or exceed the capacity visible to the process.

Every correction follows a replace-and-delete invariant. A new implementation is first connected through every real caller, configuration/API/UI boundary, artifact reader/writer, test, script, and active document and is then proven by focused and integration evidence with complete diagnostic review. Once that replacement is correct and operational, the superseded implementation, selector, fallback, alias, dependency, test fixture, and stale guidance are deleted in the same compile-green migration; old and new production paths do not remain side by side “just in case.” A compatibility path may survive only when an external persisted artifact or protocol requires a separately named, versioned, fail-closed migration boundary with an explicit retirement condition. It never remains as a silent runtime fallback or unreachable/dead code.

Examples:

| Effective logical threads | Automatic workers | Explicit request | Effective workers |
|---:|---:|---:|---:|
| 1 | 1 | none | 1 |
| 2 | 1 | none | 1 |
| 4 | 2 | none | 2 |
| 12 | 10 | none | 10 |
| 12 | 10 | 4 | 4 |
| 12 | 10 | 9999 | 10 |
| 23 | 21 | none | 21 |

The 23-thread case is not hypothetical: the CUDA VPS exposed 96 host logical CPUs through `sysinfo`, but its cgroup quota made Rust's `available_parallelism()` return 23. The correct NeoEthos worker ceiling there is 21, not 94 and not 95.

## Current inconsistencies

The current source does not enforce one answer:

- `neoethos_core::system::resolve_cpu_budget` defaults to `total - 1`; an oversized explicit value clamps to `total`, consuming the intended reserve.
- `HardwareProbe::detect` uses `sysinfo.cpus().len()`, which reports host topology rather than the process/cgroup allowance and therefore overstates VPS capacity.
- `SystemConfig::default` and `neoethos-models::cpu_threads_hint` independently compute `cores - 1`.
- `neoethos-search` leaves Rayon at its default when no override exists, which uses all available logical CPUs.
- multiple `#[tokio::main]` entry points construct runtimes before the resolved settings and execution budget are available.
- the scheduler divides `HardwareProfile::cpu_cores`, so a raw or stale host count propagates into every child assignment.
- `.cargo/config.toml` fixes every rustc process at `-Z threads=8` but does not set Cargo's job limit. On small machines that can oversubscribe; on large machines it leaves capacity unused.

These are not merely naming differences. They can make the app, search, model trainers, child processes, logs, and VPS scheduler disagree about the same run. Giving the same value to several independent pools is also not an aggregate limit: search, model training, Tokio blocking work, and two child processes could each consume the entire value concurrently.

## Chosen architecture: one budget authority plus hierarchical leases

Create a zero-dependency leaf crate, `neoethos-execution-budget`, containing portable CPU-capacity detection, pure resolution logic, immutable process-budget installation, and an RAII permit broker built from `std::sync`. It must not depend on `neoethos-core`, Tokio, Rayon, tracing, GPU libraries, or ML libraries.

This boundary is necessary because the repository contains three deliberately separate Cargo workspaces. The root engine can reach the crate through `neoethos-core`; the isolated `mcp` and `mesh` workspaces can use the same small crate by path without importing the trading engine's GPU/ML dependency graph.

The crate exposes three layers:

1. Pure, deterministic calculation from `(available_logical_threads, requested_limit)` for exhaustive unit tests.
2. Process installation from `std::thread::available_parallelism()` before any global pool or async runtime is created.
3. A process-global `CpuPermitBroker` whose initial permit count is the installed final limit and whose non-cloneable `CpuLease` values can be split, transferred, and returned by RAII.

The resolved value is immutable for the life of a process. A second installation with the same inputs is idempotent. A conflicting second installation is a startup error rather than a silent first-writer-wins condition.

The capacity record must retain all of the following so diagnostics do not conflate them:

- host logical threads, when a host inventory API can report them;
- effective logical threads available to this process;
- reserved logical threads;
- automatic worker limit;
- optional persistent, legacy-persistent, and parent-assigned limits with separate provenance;
- final effective worker limit.

Only the final effective worker limit may seed the permit broker or drive CPU-bound execution.

### Aggregate accounting contract

Every repository-controlled CPU-bound production entry point must own a lease before it starts work:

- pure Rust parallel work acquires a lease before entering a Rayon pool;
- model/native-library adapters receive the lease width and configure their library's **total** CPU-worker count to no more than that width;
- CPU-heavy Tokio work acquires a lease before `spawn_blocking`; ordinary `tokio::spawn` remains for I/O and short orchestration only;
- a managed child process consumes a parent lease for its entire lifetime and receives that exact width through `--cpu-threads`;
- GPU feeders and CPU fallbacks consume leases, while device kernels do not.

Acquisition completes before work is submitted to Rayon or Tokio, so pool workers never wait for permits while holding work needed by the lease owner. Code holding a lease may split that lease for nested work, but must not acquire fresh permits; debug assertions and the API shape reject nested acquisition to prevent deadlock.

The leaf crate exposes immediate `try_acquire` and a blocking wait used only by a dedicated coordinator thread or a synchronous top-level CLI thread. Async handlers never wait on a `Mutex`/`Condvar` and never call blocking acquisition on a Tokio core worker. The app-side adapter submits an `AdmissionRequest` to one dedicated coordinator thread and awaits a Tokio oneshot; cancellation removes or marks the queued request without needing the permit, and child-exit/lease-drop wakes the coordinator. Child reservations have explicit priority over opportunistic local work, with FIFO ordering inside each priority. Thus permit scarcity delays the job, not the runtime responsible for heartbeat, stop, cancellation, and child cleanup.

Rayon pools are no longer independent authorities. Search and model code execute through a `BudgetedCpuExecutor`: it creates or selects a pool whose width equals the admitted lease and holds that lease until all scoped work completes. A cached pool may retain idle OS threads, but it cannot execute CPU work without a matching lease. The existing global-search, local-trainer, and native-model paths must all be routed through this executor or a native adapter with the same lease contract. Repository checks inventory direct production uses of Rayon, `spawn_blocking`, OpenMP/native thread setters, and `num_cpus` so an unmanaged path cannot silently reappear.

The inventory also covers synchronous CPU-heavy work executed inline on async core workers, not only calls already labelled `spawn_blocking`. JSON/CBOR/message parsing or serialization, validation over unbounded collections, hashing, compression/decompression, chart construction, and large loops in root MCP, top-level MCP, mesh, app, or desktop have checked payload/decompression/collection limits. Only bounded socket wait and measured short orchestration are I/O/control exemptions. Work above the documented small-control threshold obtains that process's local async admission before being moved off the core worker, holds the lease through decode/validate/encode/cleanup, and remains cancellable. TLS/HTTP library work is dependency-classified rather than assumed free merely because the transport is remote.

For each native library, the adapter documents from current upstream documentation whether its thread parameter includes the caller and any helper threads. The adapter translates lease width accordingly and has a concurrency probe in tests. If a library cannot be bounded at its API boundary, that backend is unsupported for concurrent production use until an OS-level containment test exists; it does not receive a guessed thread count.

### Transitive/global thread-pool policy

Repository grep is not enough because dependencies can initialize hidden global pools. The implementation inventory combines `cargo tree` feature graphs, current dependency source/documentation, environment/thread-setting APIs, and measured thread-name/concurrency probes for at least Vortex scan/decode work, ndarray-Rayon, DuckDB, Burn CPU, CubeCL CPU fallbacks, BLAS/OpenMP, and every enabled tree-model backend. Every enabled CPU backend is classified as `lease_native_width`, `exclusive_global_pool`, `single_thread_under_partial_lease`, `device_only`, or `unsupported_concurrent`; an unclassified backend fails startup when its path is requested.

Those labels have executable admission semantics. `lease_native_width(n)` reserves `n` permits for the call's declared capacity and lifetime and configures a maximum total execution width of at most `n`, including caller/helpers according to the documented adapter contract; it does not require an idle or small input to keep exactly `n` workers active. A nontrivial saturation probe proves useful parallelism exists while the correctness assertion remains `observed concurrently CPU-active workers <= n`; utilization and throughput are reported separately. `exclusive_global_pool` waits for the full installed process budget while holding zero permits, then owns all permits across backend types until completion. `single_thread_under_partial_lease` reserves one permit and is allowed only after a probe proves a maximum of one CPU-active worker. `device_only` covers only a proven host-noncomputing launch/wait, with feeder and post-processing admitted separately. `unsupported_concurrent` fails before initialization, allocation, or work whenever overlap is possible.

Every workload computes an `AdmissionPlan` before acquiring its first lease; lease promotion is forbidden. A known exclusive backend requests the full budget initially. Import admission never reads mutable source bytes, a footer, or an inner codec before the source is opened once under the admitted lease and sealed into its immutable staging snapshot. It derives a conservative plan only from explicit request metadata/declared route plus the exact locked inventory; auto-detect, compressed, or otherwise unknown routes take the worst-case union and reserve the full process budget whenever any possible backend is exclusive or unclassified. After sealing, detection against staging must be a subset of the reserved plan or the import fails without promotion or publication. Discovery/preflight holds no CPU permit, opens no mutable input, and cannot initialize a worker pool. Therefore a queued exclusive request never holds a partial lease while waiting for the remainder, source mutation cannot change the reserved class between reads, and child priority/cancellation remains enforceable. If the exact locked import graph has no exclusive backend, the inventory and overlap probe record that fact rather than relying on assumption.

The production feature-construction lane in `neoethos-data` is part of this aggregate budget. Its current nested `rayon::join`, `par_iter`, and `into_par_iter` calls may execute only inside the caller's already-admitted `BudgetedCpuExecutor` reservation. The feature builder receives that lease/context explicitly, splits work within the same admitted width, and never acquires a nested lease or escapes to Rayon's global pool. The vector-ta CUDA indicator kernel remains device work, but all host parsing, feature assembly, transfer preparation, and CPU fallback work uses the same reservation.

### Vortex-only data boundary and mandatory Polars removal

The product decision is one supported data engine: Vortex. Vortex is the sole production persisted and out-of-core columnar format and the sole scan/projection/filter layer. `Ohlcv` and `FeatureFrame` remain application-owned typed views over decoded or projected Vortex data; they are not a second storage/query backend. Canonical prices, indicator/feature values, strategy/gene weights, and signal thresholds remain `f64` through import, feature construction, Vortex storage, projection, search, signal generation, live-experience capture, and backtest evaluation; the current `FeatureData::InMemory(Array2<f32>)`, `.fstore` `f32` rows, `LiveExperience.features: Vec<f32>`, and `val as f32` feature-cube/live-row narrowing are migration defects rather than the reference oracle. Small bounded frames may be materialized as `f64` ndarray/slice memory, but a disk-backed feature frame or live-learning feature record is Vortex, not a custom file or JSONL data path. A model adapter may narrow a finite, range-checked view to `f32` only when that concrete model/backend is intrinsically `f32`; the narrowing is named in capability/training metadata and tested against the same adapter's `f64` input contract. It cannot leak back into shared feature storage, GA/search weights or thresholds, signal generation, live experience, execution, ledger, or broker arithmetic. Model adapters consume `FeatureFrame` accessors or model-native views, with typed label vectors. No model trait, trainer, ensemble adapter, test fixture, importer, or public API may expose a Polars `DataFrame`, `Series`, or `LazyFrame`, and no Polars compatibility wrapper is introduced.

The supported native-CUDA and live-decision contracts are part of that same `f64` boundary. Every floating-point host DTO, snapshot/fixture field, native device buffer, strategy weight, threshold, stop-volatility multiplier, SMC schedule/weight/gate, perturbation that alters those values, live `MlDecision` probability/gate/anomaly value, signal confidence used for veto or sizing, trade price/PnL metric, kernel parameter, ordered accumulator, and floating readback used for signal/trade/prop-firm evaluation is `f64`; identities, timestamps, counts, indices, flags, and discrete signals remain their exact integer types. Model-intrinsic f32 probabilities may exist only inside a named model adapter and must be converted to the shared f64 decision contract before they reach the trader. Changing C-compatible layouts requires one explicit ABI-version increment, synchronized Rust/C/CUDA declarations and size/alignment/offset assertions, and fail-closed rejection of the previous ABI by both host and device entry points; old bytes are never silently reinterpreted. Capability is established from the exact locked backend plus a real-device f64 compile/launch/readback probe, not inferred from a generic API accepting `f64`: the reviewed CubeCL 0.10 CUDA registration deliberately omits `FloatKind::F64`, and its Metal registration has no f64 type. Native CUDA retains `-fmad=false`. The CubeCL search/backtest evaluator and every WGPU/Vulkan/Metal/ROCm evaluator are fail-closed during the coordinated f64 type flip and then removed by the supported-hardware task; the plan does not spend work porting those retired shared/trading kernels. An exact-named model-local f32 trainer may retain a CUDA-only CubeCL/Candle/tree-library implementation only after it consumes the unified resolved NVIDIA assignment, launches real kernels on that card, exposes its adapter-local f32 boundary, and passes real-device tests with no CPU fallback. This exception never permits CubeCL to handle shared f64 features, search/backtest evaluation, signal/trade arithmetic, or a non-CUDA backend. No retiring or retained backend may silently narrow, select a nominal kernel, fall back to CPU, or report GPU execution without a launch.

The vendored, project-modified `vector-ta` is audited as executable production code rather than treated as an upstream black box. A generated manifest maps every production indicator/output/parameter plan to its scalar f64 CPU oracle, exact CUDA entry point, input/first-valid/output-shape contract, and measured status. An `_f64` symbol name is not proof: empty/no-op stubs, host-compute-then-upload wrappers, f32 buffers/casts/literals in the reachable path, missing outputs, and kernels that only resolve but do not write the expected sentinel are rejected. Every GPU-claimed feature launches a real device kernel on the assigned card and satisfies per-indicator numerical parity plus full downstream signal/trade parity. `KernelPanic`, unexplained truncation, compute failure, or an unclassified dispatch error fails the feature build; it is not converted into a silently usable all-NaN feature. Expected warmup/undefined rows use explicit validity and never become numeric zero. Permanently unsupported or duplicate outputs are excluded by one versioned schema manifest rather than repeatedly allocated, transferred, or scored; frame-dependent degenerate columns remain visible in diagnostics/validity metadata and cannot influence ranking.

A locally implemented/static-checked CUDA row remains `cuda_candidate_unverified` and is fail-closed for `GpuOnly` selection. Only the real-card validation task may promote its exact source/hash/formula identity to `real_f64_cuda` for one typed `CudaHardwarePromotionKeyV1` after current-device launch/readback, parity, launch telemetry, transfer, and no-fallback evidence; compilation or CPU parity cannot enable it. The key binds compute capability, reviewed driver/runtime compatibility, nvcc/toolkit, ABI, precision/code-generation flags, semantic source manifest, `CudaBuildManifestV1`, exact loaded artifact hash, and validated module-load path. Evidence also records the real card's stable UUID/PCI identity and session ordinal. A vector-ta row promoted on sm89/exact-cubin SASS is not thereby promoted on sm86 or sm90; vector-ta has no PTX/JIT promotion route.

Every host build first resolves one versioned `BuildHostPlanV1` before Cargo/native compilation starts. The automatic plan records `available_parallelism`, the already-reserved-two automatic worker limit, the detection source, and every visible discrete NVIDIA device's stable UUID/PCI identity, reported name, and compute capability. Its CUDA architecture set is the canonical sorted/deduplicated set of those visible compute capabilities; a 3090 resolves sm86, a 4090 resolves sm89, and a mixed host resolves both. The preflight passes the worker limit to Cargo/native scheduling and passes the same canonical architecture set through each reviewed builder adapter: vector-ta receives `CUDA_ARCHS`, while native search and retained model builders receive their documented typed inputs. Builders consume that sealed plan rather than selecting ordinal zero, inventing a default architecture, or narrowing to the first card; vector-ta may auto-detect every visible device only when no explicit cross/release set is supplied. The exact plan/hash is embedded into generated Rust/CUDA artifact metadata so runtime code can report it and intersect the packaged images with the actual `ResolvedDeviceAssignment`; a build-time card never by itself authorizes runtime support. A CUDA host build with no resolvable eligible card fails before compilation unless the caller explicitly selects a reviewed cross/release architecture matrix. That explicit matrix is the only override and is recorded as `cross_release_explicit`, never disguised as automatic host detection. CPU-only builds require no NVIDIA probe. Direct repository entry points, CI, packaging, VPS scripts, and developer wrappers all invoke the same resolver; conflicting environment/script/build-script results fail closed.

Every CUDA artifact embeds a versioned `CudaBuildManifestV1`: exact `BuildHostPlanV1` identity and resolution mode; compiler/toolkit version; canonical ordered `-gencode` entries; exact native SASS set; mandatory precision flags; ABI and semantic-source hashes; and SHA-256, logical stem, payload kind, and build provenance for each module. For vector-ta, the payload kind is exact ELF cubin, the PTX target set is empty, and no fatbin, JIT, or prebuilt-artifact input exists. A separately retained backend records any additional artifact kind or PTX target explicitly rather than lending that route to vector-ta. vector-ta rejects every non-empty `NVCC_ARGS` value before launching nvcc; only its reviewed typed controls may affect the build. Every real build input is present and tracked; missing, zero-byte, unknown-provenance, or unclassified artifacts reject.

Every module load produces `ModuleLoadEvidenceV1` even when debug logging is disabled: exact `CudaBuildManifestIdV1`, stable device UUID/PCI plus session ordinal, compute capability, driver/runtime/toolkit, module stem and exact bytes/hash, selected container, load duration, errors, and subsequent launch/readback identity. vector-ta records one inspected exact-cubin/SASS route through the single central `Module::from_cubin`; its source and feature guards reject PTX, fatbin, JIT, prebuilt artifacts, force-route controls, and alternate loaders. A separately retained backend with another module route must identify, inspect, admit, and promote that route under its own artifact key. No alternate route may inherit vector-ta's SASS promotion.

GPU acceleration coverage is reported as a stage-by-stage ratio, not a boolean. The current production engine accelerates only a subset of the vector-ta multi-period sweep even though the custom fork contains many more f64 entries; this is an incomplete GPU feature lane. The target native-CUDA path uploads each frame once, batches/streams all proven f64 indicator work on its assigned device, preserves a stable named feature schema, and hands resident f64 feature buffers directly to compatible search/evaluation stages where possible. That handoff is a shared ABI-v4 `ResidentF64FeatureBuffer`: it carries stable device UUID/PCI identity, CUDA session/primary-context identity, schema hash, f64 element/layout/strides, validity layout, allocation generation, producer readiness event/stream, and an RAII owner token. Vector-ta and native search borrow one resolved-device `CudaDeviceSession`; the consumer cannot outlive the owner/session, waits on the producer event, and rejects stale handles or device/context/schema/layout/ABI mismatch before launch. A real-device test must prove the native consumer uses the exact resident allocation with one source upload and zero intermediate device-host-device feature transfer; otherwise `GpuOnly` remains unavailable. Any missing production f64 kernel/output is implemented against the reviewed scalar oracle; it is never supplied by a CPU segment inside a GPU run. `GpuOnly` fails before allocation or feature work when any requested feature/model/search node lacks a promoted resident CUDA route or requires host materialization. `CpuOnly` loads no CUDA context. Automatic selection resolves exactly one complete lane before work begins: it may choose the complete CPU lane when no complete promoted GPU lane is available, but it never splits one run across CPU and GPU and never changes lanes after partial execution. Hybrid execution and mid-run CPU fallback are unsupported and removed rather than retained as hidden compatibility paths.

Every persisted or wire artifact that contains a `Gene`, SMC gate, shared feature value, threshold, or live decision is versioned as part of the same migration. This includes checkpoints, selected portfolios, live portfolios, streaming batch ledgers, strategy-database rows, the public SQLite `SavedStrategy` record, Prototype-A uploads, GPU snapshot fixtures, autoresearch promotion evidence, both app federation surfaces (mesh gene migration and worker portfolio submission/storage), and mesh migrant gossip. `SavedStrategy` may no longer hide weights, thresholds, or SMC values in an unversioned `JsonValue`; it uses a typed, validated f64 schema/provenance envelope and a transactional database version change. Federation submission no longer accepts `portfolio_json: String`, `trades_json: String`, or an opaque `serde_json::Value` that is counted and written as a current live portfolio: one typed envelope carries schema/capability version, immutable portfolio and ordered-feature-schema hashes, typed f64 genes/trades, run/data provenance, and finite-value validation. Each schema is bumped and the old f32-derived or unversioned version is rejected or accepted only by an explicitly named offline migration whose output is marked `precision_unrecoverable=true`; widening a legacy decimal to f64 is not represented as recovered precision. Federation and mesh advertise an f64-gene capability and use a typed versioned envelope; old or capability-unknown peers remain observer-only for gene scheduling/migration. No bare `Vec<Gene>`, opaque unversioned JSON gene payload, or raw portfolio string is accepted after the cutover.

Prop-firm limits, preset/API DTOs, challenge gates, and every downstream risk/evaluation comparison are f64 because their boundary decisions can change pass/fail status and trading eligibility. The existing f32-widening fingerprints and rounding workarounds are removed, and exact f64 boundary tests cover daily loss, total drawdown, profit target, minimum monthly profit, and downstream autoresearch/search validation. Scheduler RAM/VRAM admission derives element sizes from the actual f64 host/device layouts (including padding or structure-of-arrays choices) rather than retaining hard-coded f32 byte estimates; layout and capacity tests fail if the ABI changes without updating the estimate.

### Supported hardware and device-selection contract

The release-supported hardware matrix for this phase is deliberately narrow: AMD x86-64 CPUs for CPU execution and only NVIDIA discrete compute capabilities/module paths with a complete `CudaHardwarePromotionKeyV1`. Discovery may display another NVIDIA card as unvalidated, but strict/auto GPU execution rejects it until the full manifest/parity suite promotes its exact architecture/environment; compilation/artifact presence is labelled build-compatible, not supported. Native CUDA is the only shared f64 indicator/search/backtest lane; exact-named intrinsically-f32 model trainers may use a CUDA-only library backend under the same resolved-device contract and real-launch proof. The shipped CPU baseline is portable x86-64 and does not require repository-wide `target-cpu=x86-64-v3`, AVX2, BMI2, or FMA, so an older supported AMD cannot receive illegal instructions; proven SIMD hot paths may use runtime feature detection and dispatch. Every dispatched branch is named/inventoried and force-selectable in tests. Portable scalar and each enabled AVX2/BMI2/FMA branch must preserve identical validity and f64 feature/signal `to_bits()` results on adversarial fixtures, and—only on an exact broker-capable fixture—the same ordered trade/ledger/metric tuple. A branch using contraction, fast math, a different reduction order, or other semantics that cannot pass that contract is disabled/fail-closed rather than accepted as a performance tolerance. CPU code does not hardcode the current Ryzen or its core count, while other CPU vendors/architectures remain unvalidated and are not advertised for this release. Integrated GPUs, AMD/Intel discrete GPU execution, WGPU/Vulkan/Metal/ROCm, virtual adapters, software adapters, and unknown adapter classes are removed from production selection, configuration, feature flags, and help text after their final baseline is captured. They may be implemented again only through a later reviewed plan and real-device proof; dormant production branches and misleading fallback support are not retained.

One typed `ExecutionDevicePolicy` replaces disconnected search/model/environment selectors. It has exactly three operator intents: `CpuOnly`, `AutoNvidiaDiscrete`, and `NvidiaDevices(non_empty set)`. `CpuOnly` performs no CUDA runtime/context initialization. Auto enumerates only NVIDIA CUDA devices that pass driver, promoted compute-capability/module-path key, free-memory, ABI, f64-kernel launch/readback, build/artifact identity, health preflight, and complete requested-graph coverage, then resolves the whole run to either `CpuOnly` or `GpuOnly` before work starts. It never creates a hybrid lane or falls back after partial GPU execution. A strict GPU request fails if no selected device passes. Explicit selection may name one or many cards using a canonical device identity returned by discovery (CUDA UUID plus PCI bus id, with the runtime ordinal reported but not treated as a stable identity); input/UI order is display-only and both auto and explicit sets canonicalize to the same stable UUID+PCI sort before assignment or artifact hashing. Missing, duplicate, ambiguous, integrated, non-NVIDIA, unpromoted architecture/load path, or unhealthy selections fail before work starts. CLI, app/API, desktop, scheduler, search, every direct model trainer/adapter and training artifact, `neoethos-data` feature construction, and the vector-ta CUDA indicator lane consume the same resolved object. A config update either preflights and atomically installs the new assignment for subsequent jobs or returns an explicit restart-required `pending` versus `active` state; saving a value cannot silently leave the runtime on the old selection. The separate process-global `IndicatorComputePolicy` override is removed; no production caller parses `gpu:N`/`cuda:N`, invents `gpu:0`/`cuda:0`, constructs `GpuIndicatorEngine` with a hard-coded ordinal, or independently chooses CPU/GPU after sealed resolution. A scheduler assignment carries stable UUID/PCI identity and resolves a session ordinal only at the backend adapter. Legacy environment/string selectors are retired or translated once at sealed config load with a warning.

The current locked WGPU 29 source exposes `Instance::enumerate_adapters`, `AdapterInfo.device_type`, and the exact `Other`, `IntegratedGpu`, `DiscreteGpu`, `VirtualGpu`, and `Cpu` variants; this is used to prove the pre-removal inventory and to reject misleading name-based classification, not to preserve WGPU execution. The current source also still accepts `wgpu_integrated_gpu` in model policy and contains a stale integrated-GPU override diagnostic even though the override was deleted; those surfaces are removal defects.

All selected NVIDIA cards are available to the scheduler and are sorted by canonical identity for deterministic assignment. The proven baseline is one CUDA context/lane per card with independent symbol/timeframe/model-training jobs running concurrently. Each data/indicator/search/model job receives one resolved assigned device and promoted environment key, and its adapter resolves that stable UUID/PCI identity to the session ordinal only at launch; the same job is not redundantly fanned across cards unless a separately measured deterministic design justifies it. A single population may shard across multiple cards only after a native-CUDA multi-device test proves stable shard membership, one full f64/ABI/capability/module-load check per card, bounded host feeders, exactly-once result coverage, and a merge ordered by original work id rather than device completion time. The known CubeCL multi-device panic/CPU-fallback path is not reused. Model jobs use independent per-card assignments, not CubeCL's broken population sharder. In strict mode a device loss or artifact/load-path mismatch fails the affected run/checkpoint explicitly; it never silently recomputes on CPU, another card, or an unvalidated alternate module path. vector-ta exposes no alternate route. One-card and multi-card runs with the same seed/input must produce identical ordered indicators/validity/signals; full trades/ledger/metrics are compared only on an exact broker-capable fixture. Model training additionally records deterministic seed/input/model/artifact identity and its exact device assignment. Production support for selecting multiple cards for independent jobs requires a real process with at least two eligible NVIDIA cards and a complete promotion key for every architecture/load path used; a one-card VPS may validate only its one-card architecture subset and cannot satisfy the final integration gate. Unproven single-population sharding remains explicitly unavailable rather than blocking the independent-job multi-card baseline.

This is a mandatory first implementation phase, before the CPU-budget integration can be accepted. The current reviewed tree has not completed the earlier intended removal: Polars is a direct dependency of `neoethos-data` and `neoethos-models`, occurs in 42 Rust source/test files, and `cargo tree -p neoethos-app -i polars` reaches the production app through both crates. Those model interfaces are migrated to `FeatureFrame`/typed targets.

Runtime discovery, loading, charting, feature computation, training, backtest, and live paths accept only validated `.vortex` datasets. The explicit user import boundary remains a supported production feature: a user may supply CSV, TSV, JSON, JSONL, Parquet, Arrow IPC/Feather, or an existing Vortex file and receive a canonical Vortex dataset. The import source vocabulary is split from runtime storage identity: `ImportSourceFormat` owns those source variants, while the canonical dataset layer has only Vortex. A non-Vortex source can never be registered, cached, scanned, or returned as a runnable dataset.

The canonical generation manifest is producer-neutral. It stores the Vortex generation/schema/hash/range, typed dataset identity and bar convention, publication metadata, and one bounded opaque `ProducerProvenanceEnvelopeV1 { schema_id, canonical_payload, payload_sha256 }`; it has no source-format enum/string and runtime never interprets producer payloads. The dataset layer validates the envelope's namespaced schema id, size, canonical byte/hash binding, and manifest association only. The import boundary alone owns `ImportProvenanceV1` and `ImportSourceFormat`, serializes source format, exact immutable staging SHA-256, captured source identity/size, source schema/convention, importer version/time, and any exact numeric mapping into that envelope, and is the only production code allowed to decode that import schema for reporting. Broker capture and the legacy migrator use distinct typed producer schemas. Unknown/tampered producer payloads fail at their typed audit/report boundary but cannot make Vortex runtime branch on CSV/Parquet vocabulary or create an import/publication dependency cycle.

Dataset roots use one typed, non-lossy `CanonicalDatasetIdentity`, never a sanitized symbol string. A cTrader-bound identity includes live/demo environment, exact broker/server or account scope, required `symbolId`, exact UTF-8 symbol name as corroborating metadata, and `CanonicalTimeframe`; the protocol documents `symbolId` as unique only in a specific server environment. An external corpus lacking that broker identity uses a separate explicitly non-broker-real namespace plus its exact UTF-8 declared name and provenance, never impersonates a cTrader symbol, and cannot pass a broker-real gate. Path components are a reversible, versioned base32hex encoding of canonical length-prefixed bytes (fixed field order, integer endianness, and variant tags), not punctuation stripping, Unicode normalization, lowercasing, or lossy replacement. The manifest stores the typed identity and recomputes the component; the dataset-scoped lock keys the same canonical bytes. Reject invalid UTF-8/control/NUL, overlength, decode/noncanonical encoding, case ambiguity, Windows ADS/reserved-name/device-name forms, separators, dot segments, and any duplicate/collision. Containment and no-symlink/junction/reparse checks cover the configured root and every symbol/timeframe/generation component before lock, read, hash, rename, or delete.

The existing human-readable `symbol=EURUSD/timeframe=M5` layout is legacy input after this cutover, not a second runtime layout. One strict offline migration utility validates old manifests/bytes, takes an optional operator-supplied broker mapping proven against captured account symbol metadata, decodes and rewrites only a specifically versioned/proven old schema into the generation/CAS protocol, and publishes all-or-nothing without deleting the source. It never byte-copies data whose meaning depends on read-time timestamp magnitude inference, sorting, deduplication, or missing-to-zero repair; an explicitly declared legacy unit may use checked exact conversion, while an ambiguous/unknown schema fails. Without verified broker mapping it can create only an external/non-broker-real identity; it never invents environment, account/server scope, or `symbolId` from a folder name. Runtime rejects legacy roots after the migration version. Broker bootstrap/download writers construct broker-bound typed identities directly; CLI, config resolution, search, UI, GitHub snapshot extraction, tests, and docs use typed manifests/resolution rather than formatting paths. A whole-source guard rejects legacy direct `Path::join("symbol=...")`/`timeframe=...` constructors outside the migration utility and exact reporting displays.

`CanonicalTimeframe` is the exact declared cTrader enum set `M1,M2,M3,M4,M5,M10,M15,M30,H1,H4,H12,D1,W1,MN1`; filename/path/header inference may only corroborate it and disagreement fails. The ±5% median-spacing heuristic is deleted. For fixed minute/hour frames, every UTC bar-open minute lies exactly on that period's epoch-aligned grid and every adjacent delta is a positive integer multiple of the period; missing multiples are legal because cTrader creates no trendbar when no tick arrives, so a weekend/no-tick gap is not silently filled. D1, W1, and MN1 are separate calendar-grid variants, never approximate fixed durations: their exact UTC anchor/calendar rule must be established from official protocol plus captured broker fixtures before that variant is enabled, otherwise import fails closed as unsupported. Tests include M1 mislabeled M5, off-grid timestamps, a legitimate missing-period/weekend multiple, and each proven calendar boundary.

The app `/data/import` workflow and the CLI import command call one shared import service. A mutable path source must first acquire a strong platform `SourceSealV1`; metadata plus repeated reads are not claimed to prove an atomic snapshot against an uncooperative writer. On Windows the service opens `GENERIC_READ` with only `FILE_SHARE_READ` (no write/delete sharing), so a conflicting existing or later write/delete/rename handle fails with a sharing violation. On supported local Linux filesystems it opens the regular file read-only with `O_NOFOLLOW`, establishes an `F_SETLEASE/F_RDLCK` read lease before reading, and watches the already-open canonical parent directory for modify/move/delete/create/overflow events. One process-wide `SourceSealCoordinator` OS thread owns a reserved real-time-signal range and `signalfd`; each live lease gets a unique signal slot, `F_SETOWN_EX(F_OWNER_TID)` targets that coordinator, `F_SETSIG` selects the slot, and the coordinator validates `{signal slot, si_fd, seal generation}` before cancelling only the matching copy. Lease release uses an acknowledged unregister/drain barrier before its fd or signal slot can be closed/reused, so a delayed signal cannot cancel another import. Seal-slot availability is part of admission: a request waiting for a slot holds no CPU permit, and the coordinator/broker grants the slot and CPU lease together. A conflicting existing writer, unsupported lease/filesystem, queue overflow, lease-break signal, or namespace event aborts before publication. The signal-aware copy cancels and releases promptly rather than waiting for the kernel lease-break timeout. Other path/filesystem/platform routes are typed unsupported until an equally strong writer-exclusion or atomic-snapshot primitive is proven. A streamed API upload instead writes directly into a private service-owned staging object and has no mutable user path. While the seal is held, the service opens the content once, bounded-copies/hashes it into a private non-aliased staging snapshot, flushes/fsyncs and reopens/verifies that snapshot, verifies final handle/path identity and an empty seal-event log, and only then releases the source seal. A writer already holding the same inode makes seal acquisition fail; rename-away, unlink, same-path replacement, and same-inode/path ABA during acquisition/copy are blocked or recorded and fail. Format detection, parsing, decompression, and validation consume only staged bytes after the seal, so a user change after release cannot alter the result and is recorded as after-snapshot state. `ImportProvenanceV1.source_sha256` inside the opaque producer envelope is the exact verified staging hash consumed by every parser, never a hash from a separate mutable read. The service detects or validates the declared source format only inside that boundary, streams bounded batches, maps aliases through an explicit schema contract, preserves `i64` millisecond timestamps and canonical f64 prices/volume semantics, and fails the whole import on a malformed, null, non-finite, inconsistent, or schema-ambiguous market row instead of silently dropping it or synthesizing a timestamp. OHLC prices must be finite and strictly positive; optional broker volume must be finite and non-negative, so a legitimate zero-volume bar is accepted unless a documented source-schema rule says otherwise. Volume is value-affecting input to Footprint/GPU features and receives the same precision/provenance protection as price: an exact integer/decimal source is preserved in its raw canonical physical representation and derives f64 only through a versioned checked mapping; a value not exactly representable under that mapping keeps the raw value but makes the f64 volume-dependent plan unsupported rather than rounding silently. Timestamps must already be valid-range, strictly increasing `i64` milliseconds—duplicates, descending rows, unit ambiguity, sorting, deduplication, and row-index synthesis are forbidden. Declared and inferred symbol/timeframe disagreement fails with source row/context rather than being repaired.

Accepted binary Parquet, Arrow IPC, and Vortex OHLC, optional volume, and shared-feature physical columns are Float64, or an explicitly documented decimal/scaled-integer representation whose exact checked mapping and scale are recorded in provenance. Float32 price, volume, or feature source columns are rejected before cast/publication as precision-unrecoverable and can never masquerade as current canonical f64 or broker-real data. For a broker integer volume field, the exact official protocol type/unit is preserved as a raw integer column plus versioned derived-f64 semantics; conversion uses checked arithmetic and must be exact for any volume-dependent f64 CPU/GPU plan. No implicit binary numeric cast is allowed.

Canonical Vortex runtime reads/writes and broker bootstrap use the same versioned `i64` millisecond contract; they do not magnitude-infer seconds/milliseconds/nanoseconds, sort, deduplicate, or repair rows. A cTrader field is converted only from its exact protocol-declared unit with checked arithmetic and stored directly as milliseconds. The exact broker volume field type/unit is likewise taken only from official protocol plus captured payload evidence, preserved raw, and mapped to f64 under the declared checked semantic version. Missing optional volume remains absent unless captured broker/schema evidence explicitly defines another value; it is never silently zero-filled.

The importer writes, flushes, reopens, and verifies an immutable content-addressed or generation-scoped canonical Vortex file and its immutable provenance metadata before a single atomic replacement of the dataset's current-generation manifest/pointer makes it discoverable. A generation identifier is an opaque single path component under the canonical dataset root; absolute paths, separators, `.`/`..`, alternate roots, symlink/junction/reparse-point escapes, and resolved targets outside that root are rejected before any hash, read, rename, or deletion. The previously referenced generation remains intact until after the pointer swap and is garbage-collected only later, so every interruption preserves either the complete old verified generation or the complete new verified generation; sequential in-place replacement of data and metadata is forbidden. Failure leaves no discoverable partial output, and orphan candidates are swept without touching the current or prior retained generation or any path outside the canonical root. Vortex input is validated and atomically registered through the same generation protocol without decode/re-encode when safe, but publication still creates independently owned canonical bytes: a verified byte copy or platform COW clone with non-aliasing write semantics is allowed, while a mutable hard link, source-path registration, symlink, junction, or reparse alias is forbidden. Later overwrite, truncation, rename, or deletion of the user source cannot change the generation bytes/hash. Publication uses one explicit expected-generation CAS per canonical dataset identity. The request captures `expected_generation`; after CPU admission it acquires a cross-process dataset lock while holding no competing publication lock, rereads the pointer, and swaps/fsyncs only if it still equals the expected value. At most one publisher for that base succeeds; every other returns a typed conflict and may retry only as a new request based on the newly observed generation. Success returns `{generation, previous_generation, durable_commit_id}` and means the new generation was current at the atomic swap plus directory-fsync linearization point—not that no later valid publisher can replace it before the caller observes the response. It never holds the dataset lock while waiting for CPU admission. Owner identity, stale-lock crash recovery, cancellation, and cleanup are explicit; concurrent imports for different roots may proceed. Runtime `loader.rs` never auto-converts: a direct CSV/Parquet/etc. runtime path fails with an instruction to import it first. The existing `validate_f32_precision`/`F32_DOWNCAST_TOLERANCE` import gate is deleted: import never downcasts broker prices through f32 or rejects valid f64 values for failing an f32 round trip.

Pointer resolution and garbage collection share a cross-process reader-lifetime protocol. Under the dataset-root lock, a reader resolves the pointer and acquires a shared OS-backed `DatasetGenerationLease`; every scan, backtest, model run, and lazy Vortex projection/reopen holds it until the last use. GC may delete an unreferenced contained generation only after it obtains a nonblocking exclusive generation lock, so it skips every live pin even after N+1/N+2 publications. OS lock release on process death provides stale-reader recovery; timestamps or PID/age metadata alone never override a live reader.

Import is a budgeted production workload, not an exception. The app awaits coordinator admission before it creates the import `spawn_blocking` task; the CLI obtains a synchronous top-level lease before entering the shared service. The admitted lease is transferred into the job and remains live across parsing, source hashing, decompression, validation, Vortex encode/write, reopen verification, atomic publish, and complete failure cleanup. The service divides that one reservation among bounded pipeline stages rather than acquiring independent permits that could deadlock. Arrow CSV/JSON/IPC readers, Parquet decompression, compression codecs, hashing, and Vortex workers are included in the dependency-pool classification; any worker width that cannot be bounded or accounted for fails closed under the same unsupported-concurrent policy.

Bounded batches are not accepted as a memory proof by themselves. One checked `ImportLimits` contract applies before allocation at every boundary: total source/staging bytes and required free-disk reserve; CSV/TSV record and field bytes/count; JSON nesting, token/string/object/record bytes; Arrow schema/metadata/message/body/buffer and record-batch rows/columns/bytes; Parquet footer/metadata/row-group/page/dictionary compressed and declared-uncompressed bytes plus cumulative decompressed bytes and compression ratio; Vortex footer/chunk/metadata/buffer limits; and total rows/columns. Every row × column × element/offset/layout calculation is checked for overflow before allocation. A reader/codec that cannot inspect and enforce the limit before its own allocation is unsupported for untrusted production import. Failure is typed, publishes nothing, and bounds cleanup/staging work. Tests measure process peak RSS or allocator high-water and staging-disk high-water, not only batches delivered to the sink, using a giant CSV line/field, deeply nested or giant JSON token/object, huge IPC batch/body, corrupt or oversized Parquet footer/page/dictionary and decompression bomb, and oversized/corrupt Vortex chunk metadata.

The importer is Polars-free. CSV/TSV and JSON/JSONL use bounded direct/Arrow readers; Parquet uses the official Arrow `ParquetRecordBatchReaderBuilder` with a bounded batch size and projection; Arrow IPC uses its file/stream readers. Record batches convert through Vortex/Arrow interoperability or the same typed OHLCV validator, never through a DataFrame compatibility layer. Broker downloads and historical Bid/Ask capture bypass import and write versioned canonical Vortex schemas directly.

The existing feature-major `.fstore` mmap is also migrated, not grandfathered. The replacement writes a Vortex `StructArray` schema containing row identity/timestamp and named `f64` feature columns in bounded chunks, and represents out-of-core `FeatureFrame`/window state with a Vortex path plus immutable schema/range metadata. Gene/model consumers request only the named columns and row ranges they need through Vortex projection/filter pushdown; a budgeted, bounded decoded-chunk cache prevents repeated full scans without becoming a second on-disk format. Temporary feature Vortex files live in a run-scoped directory, are atomically finalized before use, and are removed by RAII on normal exit. Each active run holds an OS-backed cross-process `FeatureRunLease`; a startup sweeper may remove a contained stale run only after acquiring its nonblocking exclusive cleanup lock. Process death releases the lock, while PID/age metadata is diagnostic only and can never override a live run or be trusted across PID reuse.

The production live-experience path uses a bounded single-writer append coordinator (or a compare-and-swap/retry protocol with equivalent proof), stable record IDs, idempotent acknowledgement, bounded backpressure, and a shutdown drain. Before any order submission, it writes/fsyncs/reopens/verifies the exact f64 row, `FeaturePlanIdentity`, immutable portfolio hash, broker environment/account/symbol, request fingerprint, and stable client correlation id as a versioned immutable pending Vortex chunk/generation; only after that generation and its typed control reference are durably acknowledged may the request leave the process. A transactional control journal/manifest may store lifecycle IDs, state, and the Vortex generation/hash/reference, but no feature values or second serialized feature-row format. On broker response/event it atomically binds authoritative order/position/deal identifiers to that immutable reference, including explicit partial-fill/partial-close semantics, so account reuse cannot collide and a retry cannot invent a new learning id. Recovery reconciles intent-without-response, broker event before response, response/fill after crash, rejected/expired orders, duplicate submission/event, partial fills/closes, and completed deals against authoritative broker truth. If the exact cTrader request/correlation/idempotency behavior is not proven for an ambiguous intent, the system does not resubmit, reconstruct the missing row, or train from it: it emits a durable integrity error and excludes the ambiguous lifecycle fail-closed. The pending-to-completed transition atomically/idempotently moves or adds manifest ownership of the same verified Vortex row reference under duplicate or out-of-order events; it never rewrites the feature row into a journal/SQLite/custom binary. It swaps manifests without lost updates when multiple symbol loops finish concurrently; an accepted record appears exactly once after success or crash recovery. Every current record carries an immutable portfolio artifact hash plus the canonical feature-plan identity, rather than only a mutable path and positional vector. Training partitions by that identity and rejects equal-length but differently named/ordered/defined rows. The counter and offline trainer scan only the current versioned Vortex schema whose feature list was captured as f64. Legacy JSONL rows were already narrowed to f32 and lack a provable `FeaturePlanIdentity`; the one-time utility may preserve them only in a distinct archive envelope marked `precision_unrecoverable=true` and `feature_identity=unknown_legacy`, converting all-or-nothing. It never fabricates a current identity from names, length, or portfolio path, and archive rows are excluded fail-closed from current training, promotion, and live eligibility even when their shape matches. The synchronous utility performs execution-budget preflight and holds a top-level lease through bounded JSONL parse, validation, archive Vortex verification, publication, and failure cleanup. No `.fstore` writer, reader, extension, compatibility fallback, production current/pending live-feature row outside Vortex, production live-experience JSONL path, or shared feature `f32` narrowing remains after parity and performance gates pass.

One canonical `FeaturePlanIdentity` prevents a mathematically corrected indicator or post-processing change from being mistaken for the old semantics merely because column names/types/order stayed unchanged. Its versioned hash covers the complete ordered value-producing transformation DAG from canonical source timeframe/schema contracts to final `FeatureFrame`: source-type/input-derivation semantics; every raw/vector-ta output's formula/implementation version and exact parameters; direct-frame availability plus higher-timeframe alignment/staleness rules; normalization enablement/method/fit window plus immutable fitted-preprocessor state hash when that state changes numeric values; cross-pair derivation/alignment semantics; all other derived/post stages; warmup/first-valid/NaN/validity behavior; ordered outputs and physical schema. A timeframe is never a derived transformation node: every requested timeframe is a separately imported or broker-downloaded immutable canonical generation, and a missing one fails before feature construction. Concrete dataset/live generation hashes and ranges are excluded from this semantic identity and live separately in `DatasetFeatureArtifactProvenance`; caches and trained artifacts may combine the two, while live-training compatibility partitions by plan/fitted state rather than every data append. The reviewed vector-ta capability/implementation manifest is one typed node, not the whole identity. Both plan identity and artifact provenance are embedded where applicable in canonical feature Vortex metadata, `FeatureFrame`, resident GPU ABI metadata, training artifacts, portfolios, checkpoints, `SavedStrategy`, live experience, autoresearch evidence, federation, and mesh payloads. Any scalar, kernel, direct-frame alignment, normalization, or derivation semantic repair changes the plan identity; a new input generation with unchanged semantics changes provenance/cache identity only. Old incompatible artifacts fail closed/regenerate unless a separately reviewed migration can prove semantic equivalence.

A small shared `neoethos-feature-contracts` leaf is the only implementation allowed to construct/hash `FeaturePlanIdentity` and construct the typed `DatasetFeatureArtifactProvenance`. The plan uses SHA-256 with a fixed domain-separation prefix and identity-version tag over manually specified canonical bytes: fixed field order and variant tags; unsigned counts/lengths/integers in big-endian; exact UTF-8 bytes with u32 length prefixes; a deterministic canonical topological order of typed DAG nodes with ordered inputs/outputs/parameters; f64 parameters encoded as big-endian `to_bits()` only after rejecting non-finite and negative-zero encodings; explicit warmup/validity/convention tags; and raw 32-byte reviewed formula/capability manifest, value-affecting fitted-state, and relevant semantic-implementation payload hashes. Concrete source-generation hashes/ranges are encoded only in the separately domain-separated provenance type. Semantic implementation hashes use canonical relevant source/blob payloads plus generated manifests, not the repository commit or checkout bytes; commit/object IDs are external build provenance. Dirty RED/GREEN builds may embed hashes generated from canonicalized current relevant bytes, while Task 17/18/release compares the embedded manifest to final committed Git blobs and rejects relevant stale/dirty/index mismatch. Runtime requires only the embedded manifest and works without `.git`. Duplicate, missing, or cyclic node references reject. No JSON map ordering, platform-native integer, Rust `DefaultHasher`, Unicode/case normalization, or per-crate reimplementation is permitted. Core/data compute via that leaf; mesh, artifacts, Rust GPU contracts, and C/CUDA wire layouts carry typed identities/provenance. Golden vectors run in the leaf, core, data, mesh, and GPU-contract crates on Windows/Linux, LF/CRLF checkouts, dirty TDD, packaged no-`.git` runtime, and serialization round trips; unrelated commits with identical relevant payloads preserve identity, while a changed relevant payload changes it.

Removal acceptance is workspace-wide, not just an app feature check: no `polars` dependency declaration, package in `Cargo.lock`, result in any workspace `cargo tree`, Rust import, fully-qualified use, feature flag, or stale Polars-specific runtime setting may remain. A second whole-repository guard covers Rust, Python, shell, workflows, manifests, docs, tests, and examples. It allows non-Vortex format vocabulary only in exact shared import-service/discovery symbols and exact app/API/CLI/desktop import adapters/tests, plus the separately named one-time legacy migration utility; those adapters may select and submit a source but may not contain another parser, automatic converter, or runtime storage path. It rejects any such branch in runtime discovery/load/cache/model/live-learning paths, rejects non-Vortex canonical outputs, rejects direct `--csv` GPU-benchmark parsing in Rust or `scripts/gpu-bench/prepare_snapshot.py`, and requires `run_rented.sh`, its README, and CI to consume only a verified canonical Vortex generation/manifest or invoke the shared admitted importer first. Reporting exports such as `collate.py` summary CSV remain separately named outputs, not market-data inputs. The guard also rejects the `.fstore` format/path and shared f32 feature/weight/threshold/SMC/live-decision schemas and casts across core configuration, data, search and every persisted artifact, trader/live sizing, app experience/federation, autoresearch, mesh migration, GPU contracts, GPU implementations, CLI GPU preparation, tests, and examples while allow-listing only exact named model-local adapters and probabilities/labels that cannot affect a live veto, confidence, size, trade, ledger, or promotion decision. Until all proofs pass, the branch is an incomplete migration and must not claim either Vortex-only operation, end-to-end f64 parity, or a bounded production CPU path. We do not add `POLARS_MAX_THREADS` or a Polars scheduling adapter for code whose approved end state is deletion.

Vortex itself is still subject to the execution budget. Its current Rust interface represents tabular data as named `StructArray` fields and supports scan-time projection/filter pushdown; it is not treated as a mutable DataFrame API. Every Vortex scan, decode, compression, and write path is inventoried for dependency-owned CPU work and admitted through the same lease contract. If the locked Vortex version internally launches work whose width cannot be bounded, the affected concurrent path is marked unsupported or isolated until measurement and an upstream-supported containment mechanism prove the aggregate ceiling.

The guarantee is about admitted CPU-bound workers, not the literal number of process threads. Tokio I/O workers, sleeping cached workers, passively waiting GPU-driver threads, and short control-plane activity may exist without consuming a CPU-work permit. Active CUDA context creation, native artifact parsing/loading, driver-cache compilation where applicable, linker work, and concurrent per-card initialization are CPU work, not `device_only`, and must be measured/classified/admitted before they begin. vector-ta's exact-cubin module load may receive a narrower class only after a saturation probe proves its maximum active host width; it has no PTX/JIT phase. A PTX/JIT route retained by a separately named backend is supported under concurrent/strict production only when it is bounded, cancellable, and lifetime-accounted. Logs must use this exact distinction; the design does not claim a portable hard OS CPU quota.

Every shared feature cell carries explicit validity from scalar production through `FeatureFrame`, bounded Vortex chunks/projection/cache, normalization, search/model selection, trader/live gating, and CUDA buffers. A non-finite producer result, warmup, gap, stale alignment, undefined denominator, or degenerate output becomes invalid metadata; it is never rewritten to numeric zero. Normalization fits only valid cells inside the declared training partition, records that immutable fitted state, and preserves invalidity during transform. Required-feature invalid rows are explicitly ineligible for training/ranking/signal/live capture with stable row indices and reason counts; they are not silently dropped, imputed, thresholded, or sized. A model-specific imputation policy is unavailable unless it is separately named, trained only on the training partition, encoded in `FeaturePlanIdentity`, and independently reviewed; the initial release has no such implicit policy.

Calling a plan “mathematically reviewed” covers every production value-producing or aligning node, not only vector-ta. The manifest includes classic/vector-ta indicators, SmartMoneyConcept, Session, Regime, Quantitative, and Footprint feature sources, direct canonical timeframe inputs, HTF availability/staleness, cross-pair point-in-time alignment, normalization split/fitted-state semantics, and every post-processing/derived node. No runtime path may manufacture a larger timeframe from M1 or from any other frame; each requested timeframe has its own verified generation/provenance or the run fails explicitly. Cross-pair and HTF joins are causal, never consume a future observation, require an explicit maximum staleness/no-tick rule, and make missing/stale cells invalid rather than using timestamp/value fallback. Until independent formula, causality, split/leakage, validity, and adversarial-vector evidence passes for every requested node, both strict GPU and claimed-reviewed `CpuOnly`/live/promotion eligibility fail closed; CPU/GPU agreement alone is only parity evidence.

Canonical bars use a typed, versioned `BarTimestampConvention`. The canonical runtime and broker-real schema accept explicitly evidenced `bar_open` timestamps only. Broker bootstrap maps only the exact protocol-declared trendbar convention.

“Whole-repository guard” means explicit production-facing roots: root manifests/config/toolchain files, `crates/**`, `mcp/**`, `mesh/**`, `desktop/**`, `.github/**`, `scripts/**`, production examples/tests/fixtures, and shipped `README.md`/`BUILDING.md`/help. It excludes `.git`, `target`, caches, captured build logs, and generated temporary evidence. Documentary vocabulary for removed/legacy behavior is narrowly allow-listed only in immutable `docs/audits/**` evidence and the exact approved `docs/superpowers/specs/2026-08-15-cpu-execution-budget-design.md` and `docs/superpowers/plans/2026-08-15-vortex-runtime-and-cpu-budget.md`; those files cannot be imported, parsed, or used as runtime/build configuration. Guard-test fixture literals are allow-listed by exact test path and symbol, never by a broad test/docs directory. All other shipped documentation/help remains enforced.

`SemanticSourceManifestV1` fixes the relevant-payload hash algorithm. Each entry is a canonical repository-relative forward-slash UTF-8 path plus explicit kind (`utf8_text`, `raw_binary`, or `generated` with its own declared text/binary payload kind) and SHA-256. Paths are exact Git path bytes represented as UTF-8, sorted bytewise, length-prefixed, and reject absolute/dot/backslash/duplicate/case-fold collision, symlink, reparse, and submodule entries. `utf8_text` validates UTF-8 then converts CRLF and lone CR to LF with no BOM, whitespace, Unicode, or other normalization; `raw_binary` hashes bytes unchanged. Rust, CUDA, C/C++, headers, build scripts, and text manifests are explicitly classified as text, so `.cu/.h/.cpp` cannot depend on checkout autocrlf. Generated inputs list their generator and input entries and apply the declared payload kind. Working-tree TDD bytes and final Git blob payloads pass through this identical versioned canonicalizer before comparison. The ordered manifest bytes are domain-separated and length-prefixed before the final hash.

#### Identity and cross-process lifetime clarifications

Candidate creation and garbage collection use a cross-process writer-lifetime protocol separate from the generation-reader lease. From candidate-directory creation through publish or complete failure cleanup, the writer holds an OS-backed `DatasetCandidateLease`; GC may remove an unreferenced candidate only after obtaining its nonblocking exclusive candidate lock. Process death releases that lock, while age/PID metadata is diagnostic only and can never authorize deletion of a live slow writer.

Exactly one process may own a broker-environment/account plus live-store writer domain. It acquires an OS-backed cross-process `LiveExperienceWriterLease` before accepting any order intent and holds it for the coordinator lifetime; another process fails or defers before persisting or sending an order. Process death releases the lease, and recovery acquires it before lifecycle reconciliation. The bounded coordinator serializes work inside that sole owner process.

`FeaturePlanIdentity` identifies value-producing semantics, not a concrete dataset instance. Its source nodes contain the canonical source timeframe/schema and transformation contract, while `DatasetFeatureArtifactProvenance` separately carries exact input generation hashes/ranges. A cache or trained artifact may bind `{FeaturePlanIdentity, DatasetFeatureArtifactProvenance}`, and each live row carries both, but semantic compatibility/training partitioning uses the plan plus any value-affecting immutable fitted-preprocessor state—not each new data generation. Same plan with different generations therefore preserves semantic identity while producing different provenance/cache identity.

The semantic implementation manifest hashes only the exact relevant canonical source/blob payloads and generated capability/formula manifest; the repository commit is recorded as provenance outside `FeaturePlanIdentity`. Dirty TDD builds may generate and exercise the manifest from canonicalized current relevant source bytes without an intermediate commit. Task 17/18 and release compare those embedded hashes with the final committed Git blob payloads and reject a relevant dirty/index mismatch. Runtime uses the embedded manifest and works without `.git`; an unrelated commit with identical relevant blobs leaves the plan identity unchanged, while a relevant blob change changes it. LF/CRLF checkout differences do not change the canonical hash.

`DatasetFeatureArtifactProvenanceV1` is a canonical typed mapping keyed by the exact source-node ID declared in `FeaturePlanIdentity`, not a bare list. Each source binding contains `CanonicalDatasetIdentity`, manifest schema+hash, generation ID, Vortex byte hash, `BarTimestampConvention`, and one or more consumed half-open row ranges plus inclusive timestamp bounds. Multi-generation segments for one source node are strictly ordered and non-overlapping. Canonical bytes sort by source-node ID and use the shared fixed tags/lengths/endianness; every required source node binds exactly once and duplicate, missing, extra, unknown, swapped, overlapping, out-of-range, convention/schema/timeframe-incompatible, or hash-inconsistent bindings reject. Reordering the same mapping canonicalizes identically, while swapping two datasets between HTF/cross-pair source nodes fails. Cache/live/federation/resident-GPU consumers validate plan/provenance together before use.

Each semantic manifest row carries a reviewed `SemanticSourceSetV1` closure, not only its top-level producer file. The closure includes every transitively value-affecting rolling/statistical/time/calendar/alignment/dispatch helper, generated input, build generator, parameter table, and shared macro reachable for that node. It also contains a filtered `RelevantDependencySetV1`: for each value-affecting external crate/library it records canonical package identity, source kind/registry or Git identity, resolved version, lockfile checksum or exact vendored/source-manifest hash, and the enabled feature set used by that node. A dependency enters only the rows whose production call graph/value semantics reach it, so an unrelated dependency update does not churn all identities. Compiler-selected modules/features, Cargo feature/lock/source metadata, and a build/source reachability inventory are reconciled against both declared closures; any reachable unclassified helper/dependency or declared-but-unreachable semantic source fails the build/review. Changing any relevant source or dependency payload changes the row and `FeaturePlanIdentity`; changing a proven unrelated source/dependency does not. Helper- and dependency-mutation golden tests exercise every closure class, including time/calendar behavior supplied by crates such as `chrono`.

`RelevantDependencySetV1` has one portable canonical encoding, not a per-crate serialization. Its bytes begin with `neoethos.relevant-dependencies.v1\0`, a fixed version tag, and a big-endian `u32` entry count. Entries are byte-sorted by `(package_name, source_kind_tag, canonical_source_identity)` and encode every field with an explicit tag plus big-endian `u32` byte length. Registry identity is canonical registry URL plus package name; Git identity is canonical URL plus the exact immutable revision; vendored/workspace-path identity is a slash-separated repository-relative path plus its `SemanticSourceManifestV1` hash. Absolute/local-machine paths, branch-only Git references, platform separators, and ambient registry aliases reject. Resolved version and exactly one checksum/source-manifest hash are mandatory. Enabled feature names are UTF-8 byte-sorted, length-prefixed, and duplicate-free. Duplicate package/source identities, conflicting versions/checksums/features, unknown source kinds, overflow, missing fields, case-fold path collisions, and non-canonical ordering reject before hashing. Cross-platform golden vectors cover registry, Git, vendored/path, feature reordering, duplicate/conflict rejection, and prove unrelated dependencies do not enter an affected row.

Model artifacts additionally carry a separate `ModelImplementationIdentityV1`; `FeaturePlanIdentity` alone does not identify trainer/inference semantics. The model identity domain-separates and hashes the exact trainer and inference adapter `SemanticSourceManifestV1` closures, their filtered canonical `RelevantDependencySetV1` entries (including Burn, Candle, tree/native libraries where reachable), model/backend serialization schema, label/class mapping, input/output/backend precision contract, deterministic-reduction contract, and required CPU/CUDA execution-capability contract. Session ordinals and repository commit are provenance outside the identity; actual stable training-device identity and launch evidence remain typed artifact provenance. Production creation/loading rejects missing, unknown-local-source, old-version, backend/schema/precision/device-contract, source, or relevant-dependency mismatch before inference. A selected dependency upgrade changes only identities whose reachable implementation/dependency payload changed.

A zero-external-dependency `neoethos-dataset-contracts` leaf is the sole owner of `CanonicalTimeframe`, `BarTimestampConvention`, `CanonicalDatasetIdentity`, and their versioned canonical bytes. Core/data/app/search/CLI re-export or consume those exact types; standalone mesh/GPU/feature contracts never import the data engine. Dependency direction is `neoethos-feature-contracts -> neoethos-dataset-contracts -> std/core only`, while core/data/mesh/GPU depend downward on one or both leaves; no reverse edge or duplicate temporal/identity type is allowed. Cross-workspace golden vectors prove identical canonical bytes and round trips.

## Configuration and precedence

`system.hardware.cpu_budget` remains the operator's persistent narrowing control. `--cpu-threads` remains the scheduler's per-child ephemeral narrowing control.

`models.backtest_runtime.rayon_threads` is retired as a second operator control. During one compatibility window the sealed settings loader still accepts it as a `legacy_persistent_limit`, validates it as positive, and emits one structured WARN naming the replacement. If both old and new keys exist, their minimum wins; the legacy value can never enlarge `system.hardware.cpu_budget`. The settings API and knob catalog expose only `system.hardware.cpu_budget`, and the next settings save writes only the canonical key. Search and model consumers stop reading the legacy field directly. A retired-key regression proves an old file loads with the same or narrower limit, warns, and round-trips without the old key.

Resolution order is:

```text
OS/cgroup available_parallelism
    -> subtract the fixed two-thread stability reserve
    -> narrow by system.hardware.cpu_budget, if present
    -> narrow by retired models.backtest_runtime.rayon_threads, if present
    -> narrow by parent --cpu-threads assignment, if present
    -> install one immutable process budget
```

The parent assignment is a separate startup input; it must not mutate either persistent setting. `Settings::apply_process_cpu_assignment`, which currently overwrites both fields, is removed and replaced by pure `ExecutionBudgetInputs::from_settings_and_parent`. Every cap composes by minimum. Zero in either YAML key fails in the sealed `Settings` load boundary; zero or malformed `--cpu-threads` fails argument parsing before any runtime is constructed.

Legacy `system.n_jobs` stays derived and non-settable. Its diagnostic text and computed value must use the unified resolver and say “effective logical threads minus two,” not “cores minus one.”

Required startup fields distinguish every source rather than collapsing them:

```text
host_logical_threads
effective_available_logical_threads
reserved_logical_threads
automatic_worker_limit
persistent_requested_worker_limit
legacy_persistent_worker_limit
parent_assigned_worker_limit
effective_worker_limit
active_limit_sources
```

## Startup sequence

Every executable must install the budget before creating a CPU pool or a multi-thread Tokio runtime.

For settings-aware executables (`neoethos-app`, `neoethos-cli`, and desktop), startup becomes:

1. Parse only the arguments needed to locate configuration.
2. Load and validate settings.
3. Parse any parent `--cpu-threads` cap without mutating settings.
4. Resolve and install the process execution budget.
5. Install hardware overrides first, followed by search/model/data runtime settings.
6. Construct Tokio/Rayon/native-library execution facilities.
7. Emit one structured startup record with the complete capacity calculation.

The `#[tokio::main]` entry points must be replaced with small synchronous entry points that build a Tokio multi-thread runtime using the resolved worker limit and then call an async body. The settings-free top-level `mcp` and `mesh` sidecars install the automatic or parent-assigned budget before building their runtimes.

### Production entry-point matrix

| Entry point | Settings source | Parent cap | Runtime action |
|---|---|---|---|
| `crates/neoethos-app/src/main.rs` | explicit `--config` | accepted when scheduler-spawned | synchronous preflight, then bounded Tokio runtime |
| `crates/neoethos-cli/src/main.rs` | canonical sealed settings | `--cpu-threads` | install budget before any search/model override or command |
| `desktop/src-tauri/src/lib.rs` | resolved desktop `config.yaml` | none today | synchronous seed/load, custom Tokio handle, then Tauri builder |
| `crates/neoethos-mcp/src/main.rs` | root control-plane config | optional parent cap | synchronous preflight, then bounded Tokio runtime |
| top-level `mcp/src/main.rs` | sidecar config | desktop `--cpu-threads` when managed | synchronous preflight, then bounded Tokio runtime |
| top-level `mesh/src/main.rs` | sidecar arguments/state | desktop `--cpu-threads` when managed | synchronous preflight, then bounded Tokio runtime |

### Desktop preflight and Tauri runtime

Desktop first-run seeding moves before `tauri::Builder::default()`. Path selection is split into a Tauri-independent synchronous `resolve_data_root()` and a seed step that writes the exact build-time bundled `resources/config.yaml` and broker metadata resource via `include_bytes!`; it no longer needs `App::path()` inside `.setup`. Seed and config-load failures keep the existing visible fail-closed dialog semantics.

After loading settings, desktop installs the budget, builds a `tokio::runtime::Builder::new_multi_thread()` with the resolved worker limit, retains the `Runtime` local for the entire blocking Tauri event loop, and calls `tauri::async_runtime::set(runtime.handle().clone())` exactly once **before** `tauri::Builder::default()`. Tauri's current contract says the underlying runtime must not be dropped and `set` panics if a runtime was already installed. Pure ordering tests prove no Tauri builder or plugin/setup hook can run first; a packaged first-run test proves the embedded seed and resolved editable file are byte-identical before settings migration.

Tokio thread count is a ceiling on runtime workers, not a claim that all threads are continuously busy. CPU-heavy work must still be routed through the budgeted Rayon/native-library lanes; blocking training must not be allowed to multiply unchecked behind Tokio tasks.

## Hardware profile and truthful reporting

`HardwareProfile` must stop using a raw `sysinfo` CPU count as schedulable capacity. Host inventory and live effective capacity are separate facts.

The existing serialized profile remains backward compatible and does **not** acquire an authoritative worker-limit field. Its legacy `cpu_cores` remains inventory-only so old files and APIs continue to deserialize, but scheduler/workload-planning constructors must receive the ephemeral installed `ExecutionBudget` explicitly. A profile captured on a 96-thread host and loaded inside a 23-thread cgroup therefore plans with 21 permits. Old and current profiles have the same exact behavior: they deserialize their inventory, and live planning ignores that inventory for worker capacity. A regression fixture asserts this result rather than relying on “conservative normalization.”

Logs and APIs use the term “logical threads” or “workers,” not physical “cores,” unless physical cores were actually measured. Mesh/app/desktop reporting exposes separately labelled `totalHostLogicalThreads` inventory and `totalSchedulableWorkers`, plus the number of peers with unknown capacity; only a current positive `effective_worker_limit` contributes to schedulable capacity. Legacy observer inventory never inflates the worker total. The headless keep-alive line must report the resolved worker limit and the effective logical-thread count instead of `num_cpus::get()`.

If `available_parallelism()` fails, execution falls back to one worker and emits WARN with the detection error and fallback. If a requested limit is reduced, startup emits INFO containing requested and effective values. A conflicting late installation is ERROR and aborts startup.

## Pool and scheduler integration

- Search removes `None => Rayon default` and enters parallel evaluation only through a lease-backed executor.
- The model parallel trainer does not own a second free-standing allowance. Its outer concurrency receives a parent lease and splits it; each per-model/native adapter receives only its child lease.
- XGBoost, LightGBM, CatBoost, statistical trainers, and other native libraries receive the per-workload lease width, never an independent `num_cpus::get()` result. Adapter-specific thread semantics are documented and tested rather than assumed uniform.
- CPU fallbacks and GPU feeders use the same broker. A GPU kernel launch itself does not hold CPU permits while the host thread is merely waiting, unless post-processing is active.
- The scheduler receives `&ExecutionBudget`/permit broker explicitly, never `HardwareProfile::cpu_cores`.

### Fixed child reservations

Dynamic recomputation of `parent_limit / active_children` is removed because already-running children cannot be resized. At scheduler construction, the planner chooses a maximum simultaneous child-slot count from RAM/GPU policy, clamps it to the parent permit count, and deterministically partitions the parent permits into fixed slot widths:

```text
slots     = min(configured_simultaneous_children, parent_limit)
base      = parent_limit / slots
remainder = parent_limit % slots
slot[i]   = base + (i < remainder ? 1 : 0)
sum(slot) = parent_limit
```

Before a child is spawned, the parent acquires the chosen slot's permits, passes that fixed width as `--cpu-threads`, and holds the lease in `RunningItem` until normal exit, error, cancellation, or crash cleanup. A running child is never resized. If no complete slot is available, admission waits. Unoccupied slots remain available to parent in-process work only through ordinary leases; child admission has priority so temporary local work cannot starve a queued slot. Tests cover every admission/completion order and prove the sum of live child reservations plus live parent leases never exceeds the parent limit.

Desktop-managed sidecars use the same lifetime reservation path rather than raw `Command::spawn`. Mesh receives one fixed permit by default because its production duties are I/O/orchestration. MCP receives one composite subtree reservation sized by the validated desktop `mcp_subtree_cpu_threads` setting; its default is one only when no stdio server is enabled. The desktop holds that original composite parent lease for the full MCP lifetime and passes the assigned width through `--cpu-threads` plus `coordination_scope=managed_process_tree`. If the complete reservation is unavailable, launch is deferred with structured INFO instead of partially reserving or creating an unbudgeted child. Every child computes `local_effective = min(parent_assignment, child_automatic_limit)`, where `child_automatic_limit` is that process's independently resolved `available_parallelism() - 2` result. The parent continues reserving the original assignment; the child uses only `local_effective`, reports any unused reserved width, and never lends or double-reserves the difference. The same re-clamp protects mesh, MCP, and stdio descendants when affinity/cgroups are tighter than the parent.

The top-level MCP sidecar's configured stdio servers are managed grandchildren, not free external work. Each `ServerCfg` declares a validated CPU capability and width before spawn. A managed MCP installs a local broker whose total is its `local_effective`, reserves its declared sidecar/control width, subdivides only the remainder among stdio children, and never acquires a second process-tree reservation. Each stdio process receives a fixed assignment from that remainder and re-clamps it again with the same `min(parent_assignment, child_automatic_limit)` rule. Each local child lease moves into `RunningService` and survives spawn, duplicate replacement, cancel, wait, error, crash cleanup, and shutdown join. Excess servers queue under child priority. Fixed args/environment propagate the assigned width when the server supports it. An uncooperative command whose CPU width cannot be bounded is rejected or placed under proven OS containment. For remote HTTP, only bounded socket waiting and short orchestration are I/O-only: request/result `serde_json::Value` encode/decode/validation, HTTP/TLS/decompression CPU work, and tool-list/result traversal obey hard payload/decompressed-output/depth/count limits and use the MCP local broker when above the short-control threshold. An independently launched MCP has no desktop lease, resolves its own process-local `available_parallelism - 2` budget once, and uses the identical subdivision rules with `coordination_scope=process_local`.

Independently launched NeoEthos binaries have no parent from which to obtain a cross-process lease and therefore install their own process-local ceiling. The startup record explicitly says `coordination_scope=process_local`; this design does not claim an OS-wide quota across unrelated launches. Every child that NeoEthos itself spawns is coordinated and uses `coordination_scope=managed_process_tree`.

### Mesh wire compatibility

Existing mesh JSON fields named `cpu_cores` remain accepted as a legacy alias for host inventory during capacity protocol v2. New payloads add `host_logical_threads` and `effective_worker_limit` with distinct meanings; peers must never sum `cpu_cores` as schedulable capacity. Mixed-version fixtures prove old peers still deserialize while new scheduling uses only the explicit effective field. The legacy alias is emitted only by v2 before `2026-12-31T00:00:00Z`; capacity protocol v3 and every process at/after that deadline stop emitting it, while decoding remains inventory-only/observer-only. An injected-clock boundary test makes this retirement enforceable rather than advisory.

A peer announcement without a valid positive `effective_worker_limit` has `capacity_state=unknown`, is observer-only/unschedulable, and emits one structured WARN with its protocol version and an upgrade requirement. There is no fallback to legacy `cpu_cores`, no invented one-worker assignment, and no remote work dispatch to that peer. Once an upgraded announcement supplies the field, normal admission may begin.

## GPU interaction

The CPU budget does not reduce GPU kernel occupancy, GPU batch width, CUDA streams, or the number of available cards. It limits CPU feeders, preprocessing, orchestration, and CPU fallbacks.

GPU-present paths must continue to execute real GPU kernels or fail loudly. No CPU budget mechanism may silently turn a requested CUDA/WGPU operation into a CPU implementation. When several cards or GPU workloads run concurrently, their CPU feeder shares come from the same parent worker limit.

CPU/GPU numerical parity and real-card performance remain separate validation gates. A successful CPU-budget build does not constitute GPU validation.

## Trading arithmetic and broker-truth invariance

This CPU scheduling change must not change any formula, unit, rounding rule, or input for spread, commission, swap, pip/tick value, lot sizing, risk, margin, conversion, or PnL. It must not add or preserve a constant, “typical” value, OHLC-derived proxy, hourly mean, or missing-field-to-zero fallback and then describe that result as broker-real.

The broker-truth remediation is a separate design/release gate. Its non-negotiable boundary for this work is:

- live truth comes from the exact cTrader account/symbol contract, broker Bid/Ask events, broker unrealized-PnL response, and `ProtoOAClosePositionDetail`/deal records;
- historical spread is the contemporaneous `ask - bid` reconstructed by replaying both broker quote streams in timestamp order, not candle `open - close`, not a fixed symbol field, and not a UTC-hour average. Bid and Ask updates need not share identical timestamps, so the broker-truth design must define and test last-known-quote, staleness, and any trading-session reset semantics from official protocol evidence plus captured broker behavior rather than perform a naive exact timestamp join or invent an unconditional reset;
- cTrader historical Bid and Ask ticks are requested separately in windows of at most seven days and paginated by the broker response; actual broker retention must be proven with a read-only account/environment probe that records requested ranges, raw page boundaries, earliest/latest ticks, empty/errors, and probe time rather than inferred from the timestamp schema or one successful range;
- if the selected historical range lacks synchronized broker Bid/Ask and conversion-leg coverage, that run is unsupported and fails before financial evaluation. There is no heuristic `scenario=approximate` escape: scenario labels may select among exact captured broker datasets/contracts but may not synthesize spread, commission, pip value, swap, conversion, PnL, or risk inputs;
- missing cTrader fields remain unsupported/fail-closed until official protocol evidence, captured raw payloads, and a demo-account reconciliation establish the broker's behavior.

Until that separate broker plan passes, current flat/hourly/typical spread, default pip-size, operator-estimated commission/cost, OHLC proxy, missing-to-zero, and every heuristic `scenario=approximate` arithmetic route are disabled before financial evaluation, not merely barred from promotion. Historical search/backtest, promotion, Risky Mode, and Prop-Firm Mode remain unavailable wherever exact captured broker inputs are incomplete; live PnL/risk decisions use the broker's authoritative responses or live trading is disabled. Scenario selection may only choose fully broker-sourced captured inputs under their exact provenance. This infrastructure plan may integrate only behind those fail-closed capability gates and is not a complete-bot release.

The CPU regression uses one immutable captured broker fixture containing exact metadata units, Bid/Ask events, conversion legs, commissions, swaps, and closed-deal truth. The fail-closed broker-truth gate is installed before this regression. Until the separate broker replay implementation can consume and reconcile every required captured field, workers `1` and `auto` must return the same typed unsupported result before any cost/PnL/risk calculation; the current engine may not compute a financial tuple from fallback formulas merely to test scheduling. Once the exact broker capability is proven, deterministic seeds plus workers `1` and `auto` must produce the same ordered trade ledger and complete metric tuple bit-for-bit. If a mathematically justified algorithm requires a non-associative parallel reduction, the design must first define a deterministic reduction tree and prove the final ledger/metrics are identical; looser tolerances do not silently replace this acceptance criterion.

Worker-count determinism is also a per-model/backend production contract, not only a search/ledger test. For every production model family and exact backend, the same immutable f64+validity input, labels/splits, configuration, seed, and `ResolvedDeviceAssignment` run with worker width one and automatic width. A backend marked reproducible must produce identical eligible-row mapping, model serialization/artifact hash, predictions/probabilities, downstream signals, status/loaded/skipped sets, and training metadata apart from explicitly separated worker telemetry. Its `ModelImplementationIdentityV1` binds the deterministic-reduction policy and allowed width semantics. A backend that can only provide `BestEffort`/nondeterministic output is typed as such and is unavailable for reproducible training, checkpoint resume, promotion, Risky Mode, Prop-Firm Mode, or profitability evidence until a stable algorithm/order is proven; it cannot silently pass because predictions look close. Independently validated stochastic research may remain non-promotable under a distinct artifact/capability identity.

## Build parallelism

Repository-default compilation uses Cargo's portable negative job count:

```toml
[build]
jobs = -2
```

Cargo interprets this as the logical CPU count plus the negative value, with a minimum of one. All repository builds and tests use the repository-pinned Rust nightly; a manifest `rust-version` is an MSRV/packaging claim and never switches the primary validation toolchain to stable. This is a repository default for concurrent Cargo jobs, not a hard aggregate guarantee over rustc internals, build scripts, CMake, Ninja, linkers, or tools that ignore Cargo's jobserver. Native build scripts must inherit/use the Cargo jobserver where supported. Representative default/native and CUDA feature graphs must exercise the vendored XGBoost, LightGBM, `neoethos-gpu-cuda`, and the custom vector-ta builder and prove jobserver/`NUM_JOBS` propagation; scripts such as `card_run.sh` derive their width from inherited/available capacity minus two instead of a fixed `JOBS=8`. Validation records and repairs every escape.

The custom vector-ta builder emits one exact cubin per kernel and requested architecture, so it remains an explicit throughput and aggregate-budget surface. Its bounded scheduler obtains one Cargo jobserver token for every concurrently active nvcc child (with coordinator/implicit-token counting documented), never derives an independent worker count, and preserves a deterministic kernel/output manifest. Each child has unique outputs and separately captured stdout/stderr; logs are replayed/classified in deterministic manifest order, while the first failure cancels and reaps all remaining children without publishing a partial capability artifact. The native search CUDA builder follows the same inherited-token rule. Cargo fingerprinting is also part of the performance contract: every read source/tool/environment input has an exact matching declaration, every watched path exists and is an input rather than generated output, and unchanged identical feature/unit graphs rerun neither the builder nor nvcc. vector-ta has no generated watch path or prebuilt-artifact input; a second-identical-build plus one-input-at-a-time invalidation test holds that source-only contract. Clean measured builds prove both the maximum live rustc/native/nvcc sum stays within the inherited `jobs=-2` budget and a nontrivial multi-kernel fixture actually uses available parallelism; unexplained near-serial utilization or full rebuild is a performance failure to profile rather than a correctness pass.

The fixed `-Z threads=8` rustc frontend setting is removed from both Windows and Linux target flags because multiplying eight frontend threads by several concurrent Cargo jobs defeats the intended reserve and hardcodes the build to neither the local machine nor the VPS. Stale explanatory references are removed from `.github/workflows/ci.yml` and `Cargo.toml` as part of the same change; repository/CI search must return no live `-Zthreads`, `threads=8`, or larger fixed Cargo-job override.

An explicit command-line `cargo -j` or external `CARGO_BUILD_JOBS` is outside the application's runtime configuration and can still override Cargo. Repository commands and CI must not set a larger fixed value. Validation records the effective host/process capacity alongside the command used.

Clean workspace checks must not depend on stale release artifacts. The current platform-specific Tauri bundle overlays name prebuilt `mcp/target/release/neoethos-mcp`, `mesh/target/release/neoethos-mesh`, and Windows `target/release/*.dll`, so a clean `cargo check --workspace --all-targets` can fail before source validation while a dirty machine can pass accidentally. Generated sidecars/native libraries move to an explicit packaging-only overlay/preflight. Normal `cargo check`/tests load only source-controlled resources. The packaging command builds the root native libraries and isolated MCP/mesh sidecars with the same job budget, verifies exact expected paths/architectures/hashes and rejects missing/stale/wrong-profile files, then invokes Tauri with the packaging overlay. CI/release workflows and `BUILDING.md` use that one command on Windows and Linux.

## Dependency-upgrade experiment

Dependency modernization is evaluated as a controlled experiment, not merged wholesale. Baseline, semver-compatible, full-breaking stable-release, and explicitly selected prerelease candidates are resolved and built with the same pinned Rust nightly in isolated worktrees for the root, `mcp`, and `mesh` workspaces. Candidate resolution explicitly ignores the package MSRV filter where supported so `rust-version = 1.91` cannot silently restrict a nightly experiment; that field remains a separately tested packaging promise and is not rewritten by the probe. The custom vendor patches for LightGBM, XGBoost, sklears, rlkit, and especially the project-modified f64 `vector-ta` remain exact-pinned and must resolve to their local paths in every candidate. Vortex is not a custom fork and is included in the full upgrade experiment; CubeCL prereleases are a separate explicit candidate rather than an accidental part of `cargo update --breaking`.

Each candidate preserves complete resolver/build/test logs, dependency-tree provenance, feature graphs, API/compiler changes, warnings/dead code, binary size, clean-build time, peak RAM, and local CPU behavior. After a strict provenance preflight, the baseline and candidate run the same immutable external multi-pair Vortex corpus with verified hashes, fixed seeds/configuration, worker counts, and ordered canonical-data/feature-validity/signal comparison. The currently published GitHub snapshot is not assumed usable merely from its paths or hashes: zero-byte completion markers, unsupported timeframe members, missing timestamp unit/convention/source schema, or heuristic financial metadata fail the preflight. It may be used only after the exact original generator/source contract is independently evidenced and each accepted member is migrated under the canonical schema; otherwise it is quarantined and replaced by a newly provenance-complete external fixture. Because any such public OHLCV corpus is external/non-broker-real, every run must produce the same typed unsupported result before trade/fill/cost/ledger/metric computation unless an exact synchronized cTrader replay for those identical symbols/timestamps is bound to it. Full trade, broker-cost, ledger, risk, and metric comparison runs only on a separately captured exact broker fixture containing time-aligned Bid/Ask, conversion legs, exact symbol/account contract, and authoritative deal/PnL truth; a detached or typical cost fixture is insufficient. On one AMD-CPU + RTX 3090/4090 Vast host candidates also run identical native-CUDA capability, f64 launch/readback, parity, occupancy, VRAM, and throughput probes with CPU fallback forbidden. The billed instance is destroyed after evidence capture.

An upgrade is never accepted because one run reports a higher win rate or profit. Unexplained changes in canonical data, features, validity, or signals are correctness failures on every corpus. Trades, spread/commission/swap/conversion costs, ledger ordering, and the full metric tuple are compared only where the exact synchronized broker capability exists; otherwise any attempted financial evaluation instead of the same typed unsupported result is itself a correctness failure. Candidate selection promotes only individually validated changes; profitability claims still require broker-truth reconciliation and deterministic OOS/CPCV evidence. Compiler effects are kept separate by holding nightly constant, while optional stable/MSRV checks are reported only as packaging compatibility.

## Tests and acceptance criteria

### Pure resolution tests

- Table-test 1, 2, 3, 4, 12, 23, and 96 effective logical threads.
- Verify the automatic result is always at least one and never above `available - reserve`.
- Verify requests of 1, below-auto, equal-auto, and above-auto only narrow or preserve the automatic result.
- Verify persistent, legacy, and parent caps compose by minimum and retain separate provenance.
- Verify `cpu_budget: 0` and legacy `rayon_threads: 0` fail sealed settings loading with the exact key in the diagnostic.
- Verify the settings API/knob catalog exposes only `system.hardware.cpu_budget`; no retired Rayon/all-logical-core/physical-pinning entry remains, and the auto help/value comes from the same effective-logical-threads-minus-two resolver used by runtime.
- On a 64-effective-logical-thread fixture, automatic installed capacity is 62 and a sufficiently parallel ingestion or inference job can request/use up to 62 under saturation; the former 8/16/2 clamps are absent. Small-work demand remains smaller, and concurrent grants never exceed 62. Per-job demand is not a second persistent capacity authority.
- Verify conflicting second installation fails and equal re-installation is idempotent in subprocess tests, or one serial process-global test binary, so `OnceLock` state cannot leak between cases.

Real-time signal numbers do not reserve pending-queue capacity. The Linux `SourceSealCoordinator` therefore also blocks and owns fallback `SIGIO`; any `SIGIO`, unknown/overflow `signalfd` record, or inability to establish that fail-closed fallback cancels every active seal and forbids publication because per-fd attribution is no longer trustworthy. Because signal masks are per-thread, every Linux import-capable app/CLI entry point blocks `SIGIO` plus the reserved real-time set on its initial synchronous thread before creating Tokio, Tauri, Rayon, or any other worker, so later threads inherit the mask; it initializes/verifies the coordinator and `signalfd`, or marks path import unsupported, before runtime construction. Startup probes the required `RLIMIT_SIGPENDING`, signal mask/ownership, and `signalfd` setup and rejects Linux path import when this contract cannot be installed. Runtime real-time-queue exhaustion never falls back to an attributed success, and new seals are admitted only after an acknowledged all-seals drain barrier.

### Integration tests

- App/CLI startup-order tests prove the initial synchronous Linux thread blocks fallback `SIGIO` and the reserved real-time set and installs/verifies `SourceSealCoordinator`/`signalfd` before any Tokio/Tauri/worker creation; a forced `RLIMIT_SIGPENDING` exhaustion after the multithreaded runtime starts exercises fallback `SIGIO`, proves every active source seal is cancelled and no generation publishes, then proves safe drain/recovery. Startup rejects Linux path import if fallback handling cannot be blocked, owned, and drained. The ordinary two-source test still proves a non-overflowing per-slot signal cancels only its matching `{slot, si_fd, generation}`.

- Update `hardware_derived_not_settable` expectations from 11/12 to 10/12 and add the oversized-request regression (`9999 -> 10`).
- Test that HardwareProbe planning uses cgroup/effective capacity, not raw host inventory, through an injectable pure snapshot.
- Test import, `neoethos-data` feature construction (including its nested Rayon work), search, model, native adapters, CPU fallbacks, GPU feeders, and scheduler consumers against one permit broker; concurrent probes assert the maximum admitted CPU-worker sum never exceeds the budget and no feature work reaches Rayon's global pool.
- Complete the Vortex-only migration first. Workspace guards prove there are no Polars declarations, lockfile packages, dependency-tree nodes, source imports/uses, compatibility wrappers, settings, non-Vortex runtime discovery/load/cache/model/live-learning branches, non-Vortex canonical outputs, `.fstore` artifacts/readers/writers, or production live-experience JSONL path. Import round-trip/tamper tests prove only `ImportProvenanceV1` interprets its schema and that `source_sha256` matches the exact sealed bytes. ## Alternatives considered

### Local fixes in each crate

Changing every `-1` to `-2` would be quick but would retain multiple authorities, different fallbacks, startup-order races, and future drift. Rejected.

### Environment variables as the primary authority

Setting Rayon, Tokio, OpenMP, and model-specific variables at launch would remain invisible to typed configuration and would still allow contradictory values. Standard third-party environment variables may remain supported at their documented boundaries, but they are not NeoEthos' source of truth. Rejected.

### OS affinity or a cross-process global semaphore

Affinity can reserve particular CPUs and a shared semaphore can coordinate unrelated processes, but both add platform-specific lifecycle and crash-recovery complexity. The current requirement is satisfied for repository-controlled CPU work by hierarchical in-process leases plus lifetime reservations for every managed child. A hard quota shared by unrelated operator-launched processes is not claimed and remains deferred unless measurements show it is required.

## Completion boundary

This design is complete only when source, tests, logs, and all three workspaces agree on the same effective limit, aggregate lease accounting passes under overlap, and the fixed broker fixture is invariant between one and automatic workers. Local compilation proves neither real-card execution nor trading profitability. The CPU-budget work must be reported separately from CUDA parity, the broader broker-truth remediation, OOS validation, and final merge to `master`.
